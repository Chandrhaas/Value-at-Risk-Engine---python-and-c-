# Risk-Engine v2.0: High-Performance Monte Carlo VaR System

A low-latency, decoupled quantitative risk engine that simulates 100,000+ stochastic market paths to calculate Portfolio Value at Risk (VaR) and Expected Shortfall (CVaR). 

Version 2.0 represents a complete architectural tear-down of the original Python script, migrating the core Geometric Brownian Motion (GBM) mathematics to a native C++ engine and transitioning to a zero-disk-I/O microservice architecture.

## ⚙️ Engineering & Architecture

### 1. Zero-Copy Memory Pipeline (Pybind11)
Standard multi-language systems suffer from serialization overhead. To eliminate this, the engine utilizes **Pybind11** to pass market data from Python directly into C++. 
* Market parameters (Covariance matrices, Mean returns) are reduced to raw C-contiguous NumPy arrays (`.to_numpy()`).
* These pointers are passed across the bridge directly into C++ memory space, allowing the engine to ingest multi-dimensional financial data in `O(1)` transfer time without expensive object serialization.

### 2. Cache-Optimized Mathematics (1D Flattening)
In standard Python, a 3x3 covariance matrix is represented as an array of arrays (pointer chasing). In the v2.0 C++ engine, the Cholesky Decomposition and Matrix Multiplication algorithms were mathematically rewritten to utilize **Flat 1D Vectors** (e.g., `L[j * assets + k]`). 
* This guarantees perfect spatial memory contiguity.
* Maximizes L1/L2 CPU Cache hits during the heaviest `O(N^3)` operations of the Monte Carlo loop.

### 3. Decoupled Microservice Topology
The system was split into discrete, highly scalable microservices:
* **The Compute Node (FastAPI + C++):** A high-speed ASGI backend that handles web-scraping (`yfinance`), statistical cleaning, and the Pybind11 execution. Protected by strict `Pydantic` schemas to ensure mathematical validity before executing C++ routines.
* **The Presentation Node (Streamlit):** A stateless frontend that communicates with the compute node exclusively via RESTful JSON payloads, allowing it to be hosted entirely independently of the heavy C++ binary.

## 📐 Theoretical Assumptions & Model Constraints

To achieve microsecond latency, this iteration of the engine relies on standard baseline quantitative assumptions. 

### 1. Mathematical Constraints (Geometric Brownian Motion)
* **Log-Normal Price Distribution:** The model assumes daily log returns are normally distributed, driven by a standard Wiener process (Brownian motion). 
* **Homoscedasticity (Constant Variance):** We calculate historical volatility once and apply it uniformly across all simulated futures, assuming variance does not change over the 1-day projection horizon.
* **Continuous Pathing:** The GBM differential equation assumes continuous price movements, meaning it does not currently account for overnight price gaps or sudden market crashes.

### 2. Market Microstructure
* **Frictionless Markets:** The simulations assume zero transaction costs, broker fees, or capital gains taxes.
* **Perfect Liquidity & Zero Market Impact:** We assume that if the Value at Risk limit is breached, the entire portfolio can be instantly liquidated at the exact calculated price without our own sell orders driving the market price down (zero slippage).

### 3. Data & Portfolio Dynamics
* **Statistical Stationarity:** The engine ingests a 1-year historical lookback window and assumes the empirical covariance matrix and mean returns will remain perfectly stationary for the forecasted time horizon.
* **Static Allocation:** The current configuration assumes an equally weighted portfolio (1/N) that does not rebalance dynamically during the simulation.

## 🔬 Roadmap: v3.0 Quantitative Upgrades

While the v2.0 upgrade solved the **computational** bottlenecks, v3.0 will focus on upgrading the **mathematical** sophistication of the simulations:

* **Random Matrix Theory (Marchenko-Pastur):** Implementing an eigenvalue-clipping filter in the Python pipeline to denoise the empirical covariance matrix before passing it to C++, mathematically isolating true market correlations from random noise.
* **Sobol Sequences (Quasi-Monte Carlo):** Replacing the standard C++ `<random>` Mersenne Twister (PRNG) with low-discrepancy Sobol sequences to ensure the simulated random shocks cover the distribution space more uniformly, achieving faster mathematical convergence.
* **GARCH(1,1) Volatility Modeling:** Upgrading from constant historical volatility to a dynamic time-series model to account for "volatility clustering" (where highly volatile days cluster together).
* **Jump-Diffusion (Merton's Model):** Injecting random Poisson-distributed "jumps" into the GBM stochastic differential equation to realistically simulate sudden market crashes and fat-tail events.
